# 막연한 개선 요청 (make-better)

사용자는 「뭐가 문제인지」 말하지 못한다. 대신 「이게 낫다」는 고를 수 있다.
그래서 설명을 캐묻지 않고, 진단과 안을 만들어 보여 주고 고르게 한다.
취향은 대신 정하지 않는다. 고르는 것만 사용자의 몫이다.

## 순서

### 1. 지금 상태를 직접 본다

기억이나 추측으로 진단하지 않는다. 대상에 맞는 방법으로 실물을 본다.

| 대상 | 보는 방법 |
| --- | --- |
| 화면 · UI · 연출 | 실행해서 화면을 찍거나, 게시된 시안을 연다 |
| 글 · 기획서 · 문서 | 전문을 읽는다 |
| 코드 구조 | 해당 파일과 호출하는 쪽을 읽는다 |
| 수치 · 밸런스 | 표와 실제 플레이 · 계산 결과를 본다 |
| 소리 · 효과음 | 소리 분석 도구로 듣는다 (아래 「소리를 다룰 때」) |

대상이 어디까지인지 모호하면 가장 좁게 잡고, 그렇게 잡았다고 말한다.

### 2. 기준점을 찾는다

「좋다」의 기준을 지어내지 않는다. 이미 있는 것에서 가져온다.

1. 사용자가 과거에 한 피드백 (메모리 · 이전 대화 · 리뷰 댓글)
2. 프로젝트에서 확정된 것 (기획서 · 규칙 문서 · 사람이 만든 실제 아트 · 스타일 가이드)
3. 같은 프로젝트에서 사용자가 만족한 다른 부분
4. 사용자가 준 참고 자료

하나도 없거나 사용자가 방향을 모르면, 묻지 않고 skill `explore-reference` 로 기준점을 찾는다.
돌아온 레퍼런스 보드가 기준점이다. 그다음 3 단계로 간다.

### 3. 진단한다

어색한 점을 3~7개 적는다. 항목마다:

* 무엇이 — 실물에서 가리킬 수 있는 구체적인 곳
* 왜 — 2 단계 기준점의 무엇과 어긋나는지
* 쉬운 말로, 한 줄씩

「전체적으로 밋밋함」 같은 가리킬 수 없는 진단은 쓰지 않는다. 문제가 아닌데 개수를 채우려 넣지 않는다.

### 4. 방향이 다른 안을 2~3개 만든다

안끼리는 **방향**이 달라야 한다. 같은 안의 색만 바꾼 것 · 강도만 다른 것은 안 하나로 친다.
(예: 「정보를 줄인다」 / 「위계를 세운다」 / 「분위기를 바꾼다」)

안마다 적는다: 한 줄 요지 · 진단의 어느 항목을 고치는지 · 대신 잃는 것.

설명이 아니라 **볼 수 있는 실물**로 만든다.

| 대상 | 안을 보여 주는 형식 |
| --- | --- |
| 화면 · UI · 연출 | 한 페이지에 현재 화면과 안들을 나란히 놓은 시안 |
| 글 · 문서 | 같은 대목을 안마다 다시 쓴 견본 |
| 코드 구조 | 대표 파일 하나의 변경 초안 (diff) |
| 수치 · 밸런스 | 현재 값과 안별 값을 나란히 놓은 표 + 결과 차이 |
| 소리 · 효과음 | 현재 소리와 안들을 음량을 맞춰 한 페이지에 놓은 청취 페이지 + 수치 비교 |

### 5. 스스로 걸러 낸다

보여 주기 전에 확인한다.

* 각 안이 진단 항목을 실제로 고치는가
* 어느 안이든 무난한 평균으로 수렴하지 않았는가 — 그랬다면 다시 만든다
* 확정된 규칙 · 문서 · 요청 범위를 넘지 않았는가

추천하는 안 하나에 표시하고 이유를 한 줄 적는다.

### 6. 멈추고 고르게 한다

진단 · 안 · 추천을 보여 주고 **여기서 멈춘다**. 고르기 전에는 원본을 고치지 않는다.
사용자가 답하기 쉽게 한다: 「2번」 「1번인데 더 가볍게」 「2번의 위쪽 + 3번의 아래쪽」 정도면 충분하다.

### 7. 고른 안을 좁혀 간다

* 고른 안을 원본에 반영한다. 섞어 달라고 하면 섞은 결과를 다시 한 번 보여 준다.
* 한 줄 피드백마다 그 부분만 고친다. 고르지 않은 부분은 건드리지 않는다.
* 반영한 뒤 1 단계와 같은 방법으로 다시 보고, 진단 항목이 사라졌는지 확인한다.
* 선택에서 드러난 취향(「이런 건 싫다 / 좋다」)은 메모리에 남긴다. 다음 번 2 단계의 기준점이 된다.

## 소리를 다룰 때

직접 듣지 못한다. 설치된 소리 분석 도구(MCP · CLI)로 듣고, 그 결과만 말한다.

* 들은 척하지 않는다. 「잘 맞는다」 「부드럽다」 는 도구가 낸 근거 · 수치와 함께 말한다. 도구가 없으면 듣지 못했다고 말하고 사용자에게 들어 봐 달라고 한다.
* 진단은 수치로 가리킨다 — 「화면보다 80 ms 늦다」 「기준 소리보다 고음이 많다」 「꼬리가 0.6 s 길다」
* 연출에 붙는 소리는 화면과 함께 본다. 녹화 영상으로 소리와 화면의 시차를 잰다.
* 안끼리 음량을 맞춰 들려준다. 큰 소리가 더 좋게 들린다.
* 도구의 점수는 취향이 아니다. 무엇인지 · 얼마인지까지만 믿고, 좋은지는 사용자가 듣고 고른다.
* 반영 뒤에는 같은 측정을 다시 해서 진단 수치가 고쳐졌는지 확인한다.

## 하지 않는 것

* 「어떤 점이 마음에 안 드세요?」 를 먼저 묻기 — 그걸 말 못 해서 온 요청이다
* 안 하나만 만들어 바로 적용하기
* 사용자 대신 고르고 끝내기 — 추천까지만 한다
* 개선을 핑계로 요청 범위 밖(다른 화면 · 다른 시스템 · 확정된 규칙)까지 고치기
* 프로젝트 지침(CLAUDE.md · 코드 규칙 · 브랜치 규칙)을 건너뛰기 — 이 스킬은 그 안에서 돈다
